Y ya que estás dentro: aprovecha para dejar el arranque bien configurado. Que algo funcione ahora no significa que vuelva a funcionar tras un reinicio.

          ❓ Guía rápida de systemd

          Las dos preguntas que nunca hay que confundir

          PreguntaOrdenQué responde
          ¿Está funcionando ahora?systemctl is-active <svc>active / inactive / failed
          ¿Arrancará solo al reiniciar?systemctl is-enabled <svc>enabled / disabled

          Son ejes independientes: un servicio puede estar activo y deshabilitado (funciona hoy, no vuelve mañana) o parado y habilitado (no funciona ahora, arrancará al reiniciar). Casi todos los «pero si ayer funcionaba» salen de aquí.

          Diagnosticar

          systemctl status <servicio>
          Estado, si está habilitado, el PID principal y las últimas líneas del registro. Es la primera orden siempre.
          systemctl list-units --type=service
          Servicios cargados. Con --all se ven también los detenidos; con --failed, solo los que han fallado.
          journalctl -u <servicio> · -n 20
          El registro de esa unidad. Aquí está el porqué de casi todos los fallos de arranque.
          ps aux
          Procesos en ejecución. Útil para cruzar quién está usando qué.

          Gobernar el estado actual

          systemctl start <servicio> · stop · restart
          Arranca, detiene o reinicia ahora mismo. No cambia nada de cara al próximo arranque.
          service <servicio> <orden>
          La sintaxis clásica anterior a systemd. Sigue funcionando porque redirige a systemctl.

          Gobernar el arranque

          systemctl enable <servicio> · disable
          Decide si arrancará al iniciar el sistema. No cambia el estado actual: disable no detiene nada.
          systemctl enable --now · disable --now
          Las dos cosas a la vez: habilitar y arrancar, o deshabilitar y detener. Es lo que casi siempre quieres.
          systemctl daemon-reload
          Recarga las definiciones de las unidades tras editar un fichero .service.

          Cuando un servicio no arranca

          El orden de trabajo es siempre el mismo: status para ver que ha fallado → journalctl -u para saber por qué → arreglar la causa → start → volver a comprobar. Si el registro habla de Address already in use, hay otro proceso ocupando el puerto: no se arregla reintentando, se arregla liberándolo.

          Y sobre todo

          Gestionar servicios requiere privilegios: sudo systemctl …. Consultar, no. Y piensa dos veces antes de detener algo cuyo nombre no reconozcas: en un servidor remoto, sshd es la puerta por la que has entrado.
